## Goal
Perform a senior-level review of the InfoDumpManager solution, verifying adherence to Clean Architecture, security best practices, and performance reliability.

## Input & Context Gathering
- **Scope**: Entire solution, with deep dives into `Program.cs` (WebAPI), Domain Entities, and Infrastructure Services.
- **Context**: 
  - .NET 8 Clean Architecture (Domain, Application, Infrastructure, WebAPI).
  - Technologies: EF Core 8, PostgreSQL, Redis, MinIO, Playwright.
  - Development Status: Phase 1-2 (Foundation).
- **Tech Stack Check**:
  - Found `InfoDumpManager.Domain` referencing `Microsoft.AspNetCore.App` (Framework Reference).
  - Found heavy external dependencies (Playwright) invoked in per-request scope.

## Review Protocol

1.  **Architecture Alignment**: Verified the "Clean Architecture" claim.
    - *Finding*: `Program.cs` in WebAPI understands too much about Infrastructure internals.
    - *Finding*: Domain Layer is coupled to ASP.NET Core Identity (`User` inherits `IdentityUser`).
2.  **Logic & Correctness**: 
    - *Critical Finding*: `WebScrapingService` creates a new Playwright instance and Browser for every request. This is a resource leak and performance bottleneck.
3.  **Security**:
    - *Critical Finding*: Hardcoded passwords and secrets in `appsettings.json` and `Program.cs`.
4.  **Maintainability**:
    - *Nit*: `Class1.cs` pollution.
    - *Nit*: `Console.WriteLine` usage.

## Findings

### Critical

| Severity | File/Location | Details |
| --- | --- | --- |
| **Critical** | `src/InfoDumpManager.Infrastructure/Services/WebScrapingService.cs` | **Resource Exhaustion Risk**: The service creates a new `Playwright.CreateAsync()` and processes a full browser launch *per request* inside `ScrapeInternalAsync`. This is extremely heavy and will cause thread/process exhaustion under load. **Fix**: Inject a Singleton `IPlaywright` instance or use a pooled browser context strategy registered in DI. |
| **Critical** | `src/InfoDumpManager.WebAPI/appsettings.json` | **Hardcoded Secrets**: The file contains literal secrets: `"Password": "dev_password_change_in_production"`, `"SecretKey": "minioadmin123"`. These are committed to source control. **Fix**: Use User Secrets for development (`dotnet user-secrets`) and Environment Variables for production. Remove these values from the committed JSON. |
| **Critical** | `src/InfoDumpManager.WebAPI/Program.cs` | **Hardcoded Fallback Secret**: `jwtSettings.Secret` seems to rely on a config value, but improper handling might default roughly. The `appsettings.json` likely contains a weak default secret for JWT. |

### Major

| Severity | File/Location | Details |
| --- | --- | --- |
| **Major** | `src/InfoDumpManager.Domain/Entities/User.cs` | **Domain Pollution**: `User` inherits from `IdentityUser<Guid>`. This couples the Domain layer to `Microsoft.Extensions.Identity.Stores`. While convenient, it forces the Domain to take a Framework Reference to `Microsoft.AspNetCore.App`. **Fix**: Decouple. Create a pure `User` domain entity and a separate `ApplicationUser : IdentityUser` in Infrastructure. Map between them. |
| **Major** | `src/InfoDumpManager.Web/Pages/Categories/Manage.cshtml.cs` | **Inconsistent Pattern Usage**: The PageModel mixes CQRS (`_mediator.Send`) for creation with direct Domain entity manipulation via `_unitOfWork` for updates (`category.UpdateName`). This bypasses the Application layer encapsulation for updates. **Fix**: Create an `UpdateCategoryCommand` and handler to maintain consistency. |
| **Major** | `src/InfoDumpManager.WebAPI/Program.cs` | **Leaky Abstraction**: `Program.cs` manually registers `CategoryRepository`, `MinioStorageService`, etc. This violates Clean Architecture boundaries; the API should not know about specific Infrastructure implementations. **Fix**: Create `DependencyInjection.cs` in Infrastructure (`services.AddInfrastructure(config)`) and Application (`services.AddApplication()`) to encapsulate registration logic. |
| **Major** | `src/InfoDumpManager.WebAPI/Program.cs` | **Improper Logging**: Use of `Console.WriteLine` in `ConfigureServices` and `ConfigurePipeline`. This bypasses the structured logger (Serilog) and hampers observability. **Fix**: Use `Log.Information()` or `app.Logger.LogInformation()`. |

### Minor / Nit

| Severity | File/Location | Details |
| --- | --- | --- |
| **Minor** | Multiple Projects | **Code Debris**: `Class1.cs` exists in `Application`, `Domain`, and `Infrastructure`. **Fix**: Delete these default template files. |
| **Minor** | `src/InfoDumpManager.WebAPI/Program.cs` | **Middleware Order**: `UseSerilogRequestLogging` is placed after some potential failure points. While mostly fine, it should ideally be as early as possible (after ExceptionHandler) to capture all request metrics. |
| **Nit** | `src/InfoDumpManager.Domain/Entities/GEM.cs` | **Defensive Copying Comments**: The comment "Create defensive copies... to prevent EF Core tracking issues" suggests a misunderstanding of how EF Core tracks Value Objects (Owned Types). New instances are fine, but EF Core handles owned types effectively without manual defensive copies if configured purely. |

### Questions / Assumptions
- **Assumption**: `WebScrapingService` is intended for high-throughput usage. If it's a background job running once a day, the Playwright issue is less critical but still bad practice.
- **Question**: Why is `Microsoft.AspNetCore.App` referenced in Domain? Is it solely for Identity?

### Follow-ups & Tests
1.  **Load Test**: Run a load test (e.g., k6) against the `WebScrapingService` endpoint. It will likely fail after <50 concurrent requests due to browser spawning.
2.  **Architecture Test**: Add `NetArchTest` rules to prevent `WebAPI` from referencing `Infrastructure` types directly (only the DI extension method).
3.  **Secret Scan**: Run a secret scanner (e.g., trufflehog) to ensure no other keys are buried in history.
